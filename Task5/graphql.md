# Миграция client-info с REST на GraphQL

## 1. Анализ Swagger-контракта

### 1.1. Ключевые сущности

| Сущность | Поля в REST | Кардинальность |
|---|---|---|
| `Client` | `id`, `name`, `age` | 1 |
| `Document` | `id`, `type`, `number`, `issueDate`, `expiryDate` | N (у клиента) |
| `Relative` | `id`, `relationType`, `name`, `age` | N (у клиента) |

### 1.2. Ключевые ресурсы и операции

| Ресурс | Метод | Путь | Возвращает |
|---|---|---|---|
| Клиент | GET | `/clients/{id}` | `Client` |
| Документы | GET | `/clients/{id}/documents` | `[Document]` |
| Родственники | GET | `/clients/{id}/relatives` | `[Relative]` |

### 1.3. Проблемы текущего REST-контракта

1. **Фрагментация данных.** Один сценарий (например, оформление ОСАГО) требует клиента + документы + родственников → 3 отдельных HTTP-запроса → ×3 RPS на `client-info`.
2. **Избыточность.** В карточке клиента до 500 атрибутов; REST отдаёт фиксированный набор полей на ресурс, клиент не может выбрать подмножество.
3. **Невозможность получить «всё, но без лишнего».** Один «полный» ресурс раздувает payload; множество мелких — множит RPS. GraphQL решает обе крайности: **один запрос, ровно те поля, что нужны сценарию**.
4. **N+1 на клиенте.** Потребители вынуждены сами склеивать данные из нескольких ответов.

### 1.4. Что должен покрыть GraphQL

- Все 3 операции REST → эквивалентные queries.
- Возможность запросить клиента с вложенными `documents` и `relatives` **одним запросом**.
- Возможность запросить только нужные поля (например, `name` + `documents { number }`).
- Возможность запросить документы/родственников отдельно (для сценариев, где клиент уже загружен).
- Пагинация для коллекций (на будущее — карточка объёмная).
- Единая точка входа — `Query.client(id)`; вложенные поля резолвятся отдельными резолверами (DataLoader для батчинга → защита от N+1 на стороне сервера).

## 3. Соответствие REST → GraphQL

| REST-операция | GraphQL-запрос | Комментарий |
|---|---|---|
| `GET /clients/{id}` | `query { client(id: "...") { id name age } }` | Ровно те поля, что нужны |
| `GET /clients/{id}/documents` | `query { documents(clientId: "...") { edges { node { ... } } } }` **или** `query { client(id: "...") { documents { ... } } }` | Два способа: отдельный query или вложенное поле |
| `GET /clients/{id}/relatives` | `query { relatives(clientId: "...") { edges { node { ... } } } }` **или** `query { client(id: "...") { relatives { ... } } }` | То же |
| «Клиент + документы + родственники одним запросом» | `query { client(id: "...") { id name documents { ... } relatives { ... } } }` | **Главный выигрыш**: 1 HTTP-запрос вместо 3 |

### Примеры запросов

**Сценарий 1. Оформление ОСАГО — нужны клиент, документы (номер+тип) и родственники (имя+тип родства), одним запросом:**

```graphql
query OsagoClientCard($id: ID!) {
  client(id: $id) {
    id
    name
    age
    documents(first: 10) {
      edges {
        node { id type number }
      }
    }
    relatives(first: 10) {
      edges {
        node { id relationType name }
      }
    }
  }
}
```

**Сценарий 2. Веб-приложение — только ФИО и возраст (минимальный payload):**

```graphql
query ClientHeader($id: ID!) {
  client(id: $id) {
    name
    age
  }
}
```

**Сценарий 3. Документы отдельно (клиент уже загружен):**

```graphql
query ClientDocuments($id: ID!, $first: Int, $after: String) {
  documents(clientId: $id, first: $first, after: $after) {
    totalCount
    edges { cursor node { id type number issueDate expiryDate } }
    pageInfo { hasNextPage endCursor }
  }
}
```

## 4. Проектные решения и обоснование

1. **Единая точка входа `client(id)` + вложенные поля.** Устраняет фрагментацию: один запрос покрывает любой сценарий. Клиент выбирает ровно те поля, что нужны (в т.ч. подмножество из 500 атрибутов в будущем — они добавляются как поля `Client` без изменения контракта).
2. **Дублирующие top-level queries `documents`/`relatives`.** Сохранены для обратной совместимости со сценариями, где клиент уже загружен; эквивалентны REST-путям. Не дублируют логику — те же резолверы.
3. **Relay Cursor Connections для коллекций.** Карточка объёмная, коллекции могут расти → пагинация обязательна. `totalCount` — удобно для UI.
4. **DataLoader на сервере.** Резолверы `Client.documents` и `Client.relatives` батчатся по `clientId`, чтобы при запросе списка клиентов не возникало N+1 к БД. Это ключевое отличие от REST, где N+1 был на клиенте.
5. **Скаляры `String` для дат сохранены как в Swagger** (совместимость). При желании — заменить на кастомный `DateTime`.
6. **Nullability.** `name`, `age`, `type`, `number` и т.д. — nullable, как в Swagger (там нет `required`). `id` — `ID!` (всегда есть). Коллекции — non-null (`!`), но могут быть пустыми массивами.
7. **Без мутаций.** Swagger содержит только GET → GraphQL ограничивается `Query`. Мутации появятся, когда в client-info добавят редактирование (сейчас редактирование идёт через другие сценарии).
8. **Безопасность и лимиты.** На уровне GraphQL-сервера: `max depth`, `max complexity`, persisted queries — защита от «дорогих» запросов, которые могут заменить собой DDoS после миграции с REST (важно, т.к. REST-фрагментация ранее ограничивала нагрузку естественным образом).
