# Проектирование продажи ОСАГО

## 1. Требования бизнеса

- Клиент заполняет заявку на ОСАГО → сервис опрашивает **все** доступные страховые компании → предложения от каждой компании появляются на экране **сразу, как только пришёл её ответ**.
- Максимальное время ожидания ответа от одной страховой компании — **60 секунд**.
- Пиковая нагрузка: **2 500 одновременных пользователей**, создающих заявку.
- Партнёрские API однотипны: `POST создать заявку` + `GET получить предложение`.
- Принято: выделить **osago-aggregator** (только отправка заявок и опрос решений, передача результатов в `core-app`); остальное оформление — в `core-app`.
- Подход к интеграции с партнёрами сохраняем таким же, как для продуктов/тарифов (изоляция отказов, event-streaming не обязателен для синхронного UX-сценария ОСАГО).

## 2. Ключевые решения по `osago-aggregator`

### 2.1. Нужно ли своё хранилище?

**Да, обязательно.** Причина — 60-секундное окно ожидания и требование «показывать ответы по мере поступления»:

- Заявка отправляется в 10 страховых компаний, ответы приходят асинхронно и в разное время.
- Нужно переживать рестарты подов (сервис в нескольких экземплярах), не терять состояние опроса.
- Нужно отдавать `core-app` частичные результаты (SSE-поток) и поддерживать повторный запрос статуса (если клиент переподключился).

Состав хранилища:
- `osago_request` — заявка (id, данные авто, клиент, статус, TTL 60 c);
- `osago_offer` — предложения по заявке (по одному на страховую компанию: статус `PENDING / RECEIVED / TIMEOUT / ERROR`, payload, время ответа);
- TTL/expiration — автоочистка старых заявок (cron/фоновый job).

СУБД — **PostgreSQL** (та же, что и в остальных сервисах). Объём мал (заявки живут ≤ 60 с + короткий audit), шардирование не нужно.

### 2.2. API, который `osago-aggregator` предоставляет `core-app`

Два синхронных REST-эндпоинта + один потоковый:

1. `POST /api/v1/osago/requests` — создать заявку и запустить опрос всех партнёров. Возвращает `requestId` (202 Accepted).
2. `GET /api/v1/osago/requests/{id}` — снапшот текущего состояния (для восстановления/поллинга).
3. `GET /api/v1/osago/requests/{id}/offers/stream` — **SSE-поток**: события `offer.received` по мере прихода ответа от каждой компании и `request.completed` в конце.

SSE выбран потому, что:
- бизнесу нужно «показывать сразу, как пришло» — push-модель;
- SSE работает поверх обычного HTTP, не требует WebSocket-инфраструктуры;
- легко проходит через Ingress/LB, поддерживает автопереподключение (`Last-Event-ID`).

### 2.3. Средство интеграции `core-app` ↔ `osago-aggregator`

- **REST** для создания заявки и снапшота (`POST`, `GET`).
- **SSE** для стриминга частичных результатов (`GET .../stream`).

Почему не Event-Streaming (Kafka) между `core-app` и `osago-aggregator`: UX синхронный, клиент ждёт в рамках одного HTTP-сеанса; Kafka добавила бы задержку и сложность без выгоды. Kafka уже используется для каталога/`PolicyIssued` — оставляем её для асинхронных сценариев, а ОСАГО — синхронный путь.

### 2.4. API для веб-приложения в `core-app`

1. `POST /api/v1/web/osago/requests` — принять заявку от клиента (проксирует в `osago-aggregator`).
2. `GET /api/v1/web/osago/requests/{id}/offers/stream` — **SSE-поток** для браузера: `core-app` подписывается на SSE `osago-aggregator` и ретранслирует события в браузер (с авторизацией клиента).

### 2.5. Средство интеграции веб-приложение ↔ `core-app`

**SSE** для стриминга предложений (в дополнение к REST для создания заявки). Это **отличается от чистого REST** — на схеме добавляем новую стрелку `Web → core-app` с типом `SSE`.

Обоснование: браузер должен получать предложения по мере поступления; SSE — самый простой протокол push-уведомлений поверх HTTP, работает через стандартные прокси, поддерживает reconnect.

### 2.6. Паттерны отказоустойчивости

| Место | Паттерн | Зачем |
|---|---|---|
| `core-app` → `osago-aggregator` (POST create) | **Timeout** | Заявка должна создаваться быстро; длинная обработка — не здесь |
| `core-app` → `osago-aggregator` (SSE) | **Timeout** (60 c) | Жёсткий бизнес-дедлайн ожидания решения от партнёров |
| `osago-aggregator` → партнёрский API | **Timeout** (на каждый вызов) | Один медленный партнёр не должен растягивать общее окно |
| `osago-aggregator` → партнёрский API | **Retry** (с backoff, идемпотентный GET) | Кратковременные сбои партнёра не должны приводить к `ERROR` |
| `osago-aggregator` → партнёрский API | **Circuit Breaker** (per partner) | Изоляция «больного» партнёра: после N ошибок перестаём его дёргать, отдаём `TIMEOUT/ERROR` в поток |
| `osago-aggregator` → партнёрский API | **Rate Limiting** (per partner) | Защита партнёров от перегрузки (2 500 пользователей × 10 компаний = 25 000 вызовов) |
| `core-app` (входящий API для web) | **Rate Limiting** (per client/IP) | Защита от всплесков и abuse |
| Web → `core-app` (SSE) | **Timeout** + reconnect | Браузер сам переподключается по SSE-спеке |

**Важно:** `osago-aggregator` сам управляет дедлайном 60 с — по истечении отправляет `offer.timeout` для тех партнёров, кто не ответил, и закрывает поток. Это гарантирует UX-требование «максимум 60 секунд».

### 2.7. Зависимость от нескольких экземпляров сервисов

Да, решение от этого зависит:

- **`core-app` и `osago-aggregator` в нескольких репликах.** Заявка создаётся на одном поде, SSE-соединение может прийти на другой. Поэтому:
  - состояние заявки/офферов — **в БД** (PostgreSQL), а не в памяти пода;
  - SSE-подписка реализуется через **Pub/Sub-механизм** внутри `osago-aggregator`: каждый под, у которого открыт SSE, подписывается на канал заявки. Практично:
    - либо **Redis Pub/Sub** (лёгкий, для 60-секундных сессий достаточно);
    - либо **Kafka с компактным топиком `osago-offer-events`** 
  - в решении берем **Kafka** — она уже есть в архитектуре, топик `osago.offer.events` с ключом `requestId`, и каждый под `osago-aggregator` читает свой партишен; `core-app` подписывается на тот же топик и ретранслирует в браузер. Это даёт масштабирование по партициям и устойчивость к рестартам.
- **Партнёрские лимиты.** Rate Limiting на партнёра должен быть **распределённым** (Redis token bucket или Bucket4j + Redis), иначе N подов × локальный лимит превысят договорной лимит.
- **Idempotency.** POST create от `core-app` содержит `Idempotency-Key`; `osago-aggregator` дедуплицирует по нему в БД, чтобы повторный запрос (retry от `core-app` или реконнект) не создавал дубликат заявки.
